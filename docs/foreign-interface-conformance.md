# Foreign-interface conformance

This inventory lists the normative items of the SystemVerilog VPI (IEEE 1800-2023
clauses 36–38, Annex K) and of the VHPI (IEEE 1076-2019 clauses 17–23, Annex B)
and records how fsim implements each one. It drives the conformance work that
precedes first-class cocotb support; rows change status as items close.

Status values:

- **done**: implemented as the clause reads, with a test.
- **partial**: implemented with a stated gap.
- **missing**: not implemented; the routine or property raises an error.
- **N-A**: does not apply to fsim, with the reason.
- **choice**: the clause leaves the behaviour to the tool; the row states fsim's choice.

Files: `vpi` = `src/app/application_vpi_foreign.cpp`, `vpi-cb` =
`src/runtime/vpi_callback.cpp`, `vpi-val` = `src/runtime/vpi_value_control.cpp`,
`vpi-std` = `src/runtime/vpi_standard.cpp`, `vhpi` =
`src/app/application_vhpi_foreign.cpp`, `vhpi-std` = `src/runtime/vhpi_standard.cpp`,
`run` = `src/app/application_run_commands.cpp`.

## VPI callback reasons (IEEE 1800-2023 38.36)

| Reason | Status | Notes |
| --- | --- | --- |
| `cbValueChange` | done | fires in the region of the change with the captured new value; NULL value for an event; `index` set for an array word |
| `cbForce`, `cbRelease`, `cbAssign`, `cbDeassign` | done | repetitive; after the statement runs, at the next safe point, with `obj` the force, release, procedural assign or deassign statement and `value` the target's resulting value, of the bits the statement acts on (38.36.1). A NULL `obj` at registration watches every statement, a net or variable only those on it; a bit-select is refused. The processes that keep a forced or assigned value applied are not statements and make no callback (`fsim.foreign.vpi-statements`) |
| `cbStmt` | partial | vpi | only with `simulate --foreign-probes` (key `simulate.foreign_probes`); otherwise `vpi_register_cb` returns NULL and `vpi_chk_error` names the option. The run keeps the kernel's debug points, as `--engine debug` does: no cached kernel image, no multithreading. Table 38-6: a block's callback runs before its first statement; a loop's runs on entry and again before each later pass (a while or repeat loop's test, a for loop's increment). A point is matched by process, file, line and column. The event control of `always @(...)` (the `vpiEventControl` that is the process's `vpiStmt`) runs its callbacks at each activation, at the process's entry point. Gaps: a statement of a generate block runs no callbacks (the process's statements are looked up in its instance's scope, not in the generate scope that declares them); a statement of a task or function runs its callbacks only when the caller is a process of the task's own instance (a hierarchical call from another instance does not: the execution point names the calling process and carries no callee instance, so the target instance of a task body cannot be told from the point; it needs the callee's scope in the call point) (`fsim.foreign.vpi-stmt`, `fsim.foreign.vpi-stmt-noprobe`) |
| `cbDisable` | partial | vpi | with `--foreign-probes`, on a named block or fork, task or function: a `disable` statement's execution point names its target, whose callbacks run at the next safe point, after the disable. Gaps: the callback runs even when the target was not active (38.36.1 runs it only for an active target): the kernel's `block_entry`/`block_exit` debug points exist only for disable targets and are not reported as execution points, so activity of a block, task or function is not observable at this layer; it needs those points (and per-process call depth for callables) reported to the execution-point hook; a system task or function call object is refused (`fsim.foreign.vpi-stmt`) |
